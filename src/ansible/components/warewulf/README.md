# Warewulf component

Implements security, head, image_prepare, publish, verify_publication, verify,
and rollback entry points for Warewulf 4.6.4 on a Rocky Linux 9 x86_64 head.
Run them through [core](../../core/README.md); the role's main entry point
deliberately rejects standalone execution. GPU provisioning is not implemented.

## Run through core

After setup and configuration, run from `src/ansible`:

```bash
ansible-playbook core/playbooks/site.yml -K -e core_action=preflight
ansible-playbook core/playbooks/site.yml -K
# After CPU nodes boot the published image:
ansible-playbook core/playbooks/verify.yml -K
```

The configured full deployment prepares Warewulf, runs Slurm, Spack and Lmod,
then publishes once. For preparation without publication, see
[the first two Warewulf phases](../../core/README.md#first-two-warewulf-phases).

## Inputs

- core_cluster supplies the verified head NIC/address, CPU image, CPU MAC/IP
  assignments and service IDs.
- warewulf_authorized_keys is required: list the existing public SSH key(s) of
  the account running Ansible. No private key is stored in configuration.
- warewulf_compute_dns defaults to 1.1.1.1 and 8.8.8.8; replace these if the site
  requires other upstream DNS servers.
- warewulf_image_source defaults to an upstream bootable Rocky OCI digest
  selected by core_cpu_image (currently rockylinux-9.5 in deployment config).
  A new name imports a new image. Changing the source of an existing name does
  not replace its root filesystem; use a new image name for that operation.
- warewulf_rpm_checksum requires a verified SHA-256; a pinned default is supplied.
  Upstream release RPMs are unsigned, so only that downloaded RPM is installed
  with its RPM signature check disabled; HTTPS certificate verification remains enabled.

## Ownership

The head phase configures DHCP/TFTP through Warewulf's host overlay and a
dedicated NFS exports.d file for the selected Spack tree. Unrelated NFS exports
are preserved. DHCP is bound to the private interface. A dedicated firewalld
zone/policy enables private provisioning and outbound NAT. The existing
NetworkManager connection's zone is changed; its address and routes are not.
Chrony is configured to serve the cluster subnet.

The image phase uses wwctl image exec with automatic builds and user sync
disabled. The shared image-functions.sh guard compares the chroot root inode
with the head root before allowing changes. Only absent image identities are
created; mismatches stop instead of renumbering accounts.

Each CPU receives a separate persistent Ed25519 SSH host key from a node-specific
overlay. The matching public host key is installed in the controller user's
known_hosts. The controller user's existing private key is used to connect;
that user's key is not generated by this role. Warewulf's automatic user SSH
setup is disabled.

For `sudo wwctl ssh`, image preparation also creates `/root/.ssh/id_ed25519`
on the head if absent, derives its public key, and adds that key alongside
`warewulf_authorized_keys` in the image. An existing private key is preserved;
an encrypted or invalid existing key stops preparation rather than replacing it.
Only the public key enters the image. A managed block in root's SSH configuration
selects this identity for CPU IPs, and publication pins each node's generated
host key in root's `known_hosts`. Root's key/configuration and known-hosts file
are checked by checkpoint observations using public-key derivation and public
configuration; private key contents are not stored in receipts.

After a full `core/playbooks/site.yml` deployment and CPU reboot into the new
image, test `sudo wwctl ssh cpu01 'id -u'` (expected result: `0`), then run
`sudo wwctl ssh cpu01 'systemctl restart slurmd'`. The local sudo prompt normally
asks for the invoking head user's password; no compute password is needed.
This works for head users already authorized to run the command through sudo.
It does not change head sudo permissions or create compute user accounts.
`warewulf_prepare` alone does not publish the changed image. GPU provisioning
remains outside the current site playbook.

Only inventory CPU nodes are adopted. The role refuses existing disk settings
or extra network devices, does not delete nodes, and does not provision the GPU.
The systemd.netname overlay gives the managed CPU NIC the name eth0.

## PXE lease and operating-system address

Like `src/shell/bin/hpc-setup` and its Warewulf scripts, provisioning uses two
address stages on the same `10.0.0.0/22` private subnet:

1. Firmware/iPXE gets a temporary DHCP lease from `10.0.1.1–10.0.1.255`.
   Warewulf's `default` DHCP template emits the pool without fixed-address
   reservations. `ignore-client-uids true` uses the MAC as the lease identity
   across boot stages; existing lease records are preserved.
2. Warewulf matches the request's MAC to the registered inventory node and
   serves its image and overlays. The NetworkManager system overlay sets the
   node's static `ansible_host` address (currently `10.0.2.1–10.0.2.3`) on eth0,
   with the matching MAC, subnet mask and head-node gateway.

Both configurations are prepared before boot. Stateless workers load the OS
into memory on each boot; there is no separate disk-install stage. Slurm, SSH,
and acceptance checks use the final static addresses. Keep those addresses
outside the DHCP pool. `10.0.1.255` is usable within this /22; `.256` is invalid.
Known MACs remain required and automatic node discovery stays disabled. A DHCP
lease alone does not enroll a new node.

Keep the upstream network separate from the entire private subnet. For example,
an upstream NAT route for `10.0.2.0/24` overrides a private `10.0.0.0/22` route
for the CPU addresses. Check `ip route get 10.0.2.1` on the head: it must select
the private interface. Preflight does not detect every overlapping route.

Initial head preparation applies this policy when no managed release exists.
For an existing release, full publication renders and validates the replacement
DHCP file privately, then activates it with the new overlays. Run the full site
playbook to apply this change; `warewulf_prepare` alone does not replace an
already published DHCP file.

## Publication and reruns

Read the [core recovery guidance](../../core/README.md#recovery-and-verification)
before deployment.
The role requires a verified RPM checksum and a digest-pinned source for new imports.
CPU nodes use inventory MAC/IP assignments on a trusted private network; no asset
keys or firmware tags are required. Existing imported rootfs
provenance still needs review. An existing private image is not proof of protection
for boot artifacts served over the provisioning network.

Image preparation edits only the working image. Final publication stages node
assignments, a frozen image/kernel, overlays, PXE-pool DHCP and a complete content
manifest. After validation, provisioning services stop briefly and one selector
switches the served release. The preceding bundle remains available while the
new release starts and is verified, so activation failure can restore it. After a
successful commit, stale bundles are deleted and only the active release remains.
There is no historical release available for rollback after that commit.
Staging omits previous `.img`/`.img.gz` archives for the CPU image being replaced,
including its generated release names, before copying the provision tree.
Unrelated images are preserved. Cleanup removes orphaned chroot symlinks whose
exact targets belong to deleted managed releases. After successful publication,
the managed CPU image has one working directory and one active release link.
The active snapshot is retained while the next snapshot and archive are built,
so temporary space for both releases is still necessary. Legacy migration
backups (`*.before-core-*`) are not removed by this cleanup.
This does not roll back installed head packages or the mutable working image.
Disk capacity and actual service/SELinux/PXE acceptance
must be checked on the target system. Core's minimum free-space check is not
an estimate of peak image-build and staging space.

A normal reconciliation creates a fresh bundle; validated core resume can skip
that phase. Final integrity/service checks still run. Verification also checks
booted CPU identity, address and read-only software mounts. The publication receipt
under `/var/lib/hpc-setup/images` is separate from phase checkpoints.

Core defaults to `core_resume=false`. Add `-e core_resume=true` to reuse a
validated matching prefix of phase checkpoints; a receipt alone is insufficient
when inputs, code or observed state have changed.

## Image and SSH troubleshooting

Image commands must exit successfully and emit a standalone `HPC_CHANGED=0`
or `HPC_CHANGED=1` completion marker. This catches scripts that stop early,
including malformed embedded configuration boundaries. For previously built
images with profile or Slurm syntax errors, follow the
[image repair procedure](../../core/README.md#recovering-images-built-with-malformed-template-boundaries).
Changes need full publication and a worker reboot to reach running nodes.

A remote root password prompt from `sudo wwctl ssh` means SSH key authentication
did not succeed. Check the published authorized keys, root SSH configuration,
host keys and the image actually booted; compute-user sudo rules do not fix it.

See the [component overview](../README.md), [local tests](../tests/README.md), and
[Warewulf 4.6 image documentation](https://warewulf.org/docs/v4.6.x/images/images.html).
